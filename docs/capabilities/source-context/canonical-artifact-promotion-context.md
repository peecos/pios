# Canonical artifact-promotion source context

This reference preserves the boundary between temporary execution state and durable owner-governed information. It does not require one storage technology, physical cloud location, user interface, or approval workflow.

## Lifecycle boundary

| Stage | Outcome | Capability or context |
|---|---|---|
| Produce work | Draft, intermediate output, or working copy exists | domain execution or derivation capability |
| Qualify result | Produced outcome is registered as execution evidence where applicable | preserve an execution result |
| Review and approve | Candidate is accepted, rejected, revised, or deferred | structured review and applicable proposal/authorization |
| Promote | Accepted content enters its designated canonical object lifecycle | promote a working artifact to canonical state |
| Clean up | Temporary workspace state is retained, archived, or removed safely | task-scoped execution-workspace lifecycle |
| Share or publish | A separate outward representation becomes accessible | sharing/publication capabilities |

A Result and a promoted artifact overlap but are not equivalent. A Result is a user-facing execution outcome; any accepted artifact may be promoted, including knowledge, configuration, documentation, or another durable object that is not presented as a Result.

## Canonical-home boundary

- Canonical home is an architecture relationship: which governed object/version is authoritative for an information class.
- The promotion capability creates or revises that canonical state. It does not make “canonical home” a standalone action.
- Physical placement, PIOS-system membership, Core-contract membership, and state treatment remain separate classifications.
- A cache, working copy, generated representation, or runtime-local file does not become canonical because it is convenient or currently active.
